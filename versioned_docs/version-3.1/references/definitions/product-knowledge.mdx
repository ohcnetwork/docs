# Product Knowledge

Technical reference for the `ProductKnowledge` module in Care EMR. For what Product Knowledge means to facility users, see the [Product Knowledge concept](../../concepts/definitions/product-knowledge.mdx).

`ProductKnowledge` is the reusable definition of a product: its coding, base unit, names, storage guidelines, and type-specific definition. Every `Product` references one `ProductKnowledge` record. A record is either instance-level (no `facility`) or scoped to one facility.

The Django model is only the storage layer: `code`, `names`, `storage_guidelines`, `definitional`, and `base_unit` are `JSONField`s whose structure lives in the Pydantic resource specs. The enums, nested shapes, and validation below come from those specs; the endpoints, scoping, and authorization come from the viewset.

## Models

| Model | Purpose |
| --- | --- |
| `ProductKnowledge` | Reusable definition of a product (medication, nutritional product, or consumable) |

`ProductKnowledge` extends [`SlugBaseModel`](../foundation/base-model.mdx), which extends `EMRBaseModel`. The shared base provides `external_id`, `created_date`, `modified_date`, and soft delete through `deleted`; `EMRBaseModel` adds `created_by`, `updated_by`, `history`, and `meta`.

`SlugBaseModel` sets `FACILITY_SCOPED = True` and adds the slug helpers `calculate_slug_from_facility`, `calculate_slug_from_instance`, and `parse_slug`. It defines no `save()`: the viewset prefixes the slug on create and update (see [Slug prefixing](#slug-prefixing)).

## `ProductKnowledge` fields

### Identity & scope

| Field | Type | Notes |
| --- | --- | --- |
| `facility` | `FK → facility.Facility` | `PROTECT`, nullable. Null means instance-level; set means facility-scoped. In the spec base's `__exclude__`; only `ProductKnowledgeWriteSpec` (create) sets it, so an update cannot move a record to another facility. Surfaced on read as `is_instance_level` |
| `slug` | `CharField(255)` | Stores the full prefixed slug: `f-<facility external_id>-<slug_value>` or `i-<slug_value>`. The viewset sets it from `slug_value` on create and update. The API's lookup field |
| `alternate_identifier` | `CharField(255)`, nullable | Secondary identifier. The UI labels it "HSN Code" |
| `status` | `CharField(255)` | Spec-constrained to `ProductKnowledgeStatusOptions` (required) |
| `product_type` | `CharField(255)` | Spec-constrained to `ProductTypeOptions` (required) |
| `category` | `FK → emr.ResourceCategory` | `PROTECT`, nullable. Classifies the record into a [resource category](../platform/resource-category.mdx). Written as a category slug string; read returns the serialized category |

### Naming

| Field | Type | Notes |
| --- | --- | --- |
| `name` | `CharField(255)` | Primary display name (required in spec) |
| `names` | `JSONField` (list), nullable | `list[ProductName] \| None`. See [ProductName](#productname) |
| `names_cache` | `CharField(2048)`, nullable | `name` plus every `names[].name`, space-joined, rebuilt on each `save()` by `set_names_cache()`. Searched by the `alternate_names` filter. In no spec; never set it from clients |

## Resource specs (API schema)

Every spec builds on `EMRResource` (`care/emr/resources/base.py`).

| Spec class | Role | Adds / behaviour |
| --- | --- | --- |
| `BaseProductKnowledgeSpec` | shared base | `__exclude__ = ["facility"]`. Fields: `id`, `alternate_identifier`, `status`, `product_type`, `code`, `base_unit` (required, UCUM-bound), `name`, `names`, `storage_guidelines`, `definitional` |
| `ProductKnowledgeUpdateSpec` | write · update | Adds `category: str \| None` (resource category slug) and `slug_value: SlugType` (required). On deserialize, resolves `category` with `ResourceCategory.objects.get(slug=...)` and sets `obj.slug = slug_value` |
| `ProductKnowledgeWriteSpec` | write · create | Extends the update spec; adds `facility: UUID4 \| None`. On deserialize, runs the update-spec logic, then resolves `facility` by external id |
| `ProductKnowledgeReadSpec` | read · list and detail | Adds `is_instance_level` (true when there is no facility), `category` (serialized resource category), `slug_config` (the parsed slug: `facility` and `slug_value`, or `slug_value` only), and `slug` |

### Validation & bound value sets

- `status`, `product_type`, `base_unit`, and `name` are required.
- `base_unit` is bound to `system-ucum-units`.
- `definitional.dosage_form` is bound to `system-medication-form-codes`, `ingredients[].substance` to `system-substance`, and `nutrients[].item` to `system-nutrients`. `code` and `intended_routes` stay free `Coding`s.
- `slug_value` uses `SlugType`: 5–50 characters, starting and ending with a letter or digit, and containing only letters, digits, `-`, and `_`.
- Create and update reject a slug that already exists in the same scope (the same facility, or instance level), compared without case, with the validation error "Slug already exists.".
- For a facility record, the viewset returns 404 for an unknown `category` slug.

### Server-maintained behaviour

- `facility` is set only on create, from `ProductKnowledgeWriteSpec.facility`.
- The viewset prefixes `slug` on create and update; the model rebuilds `names_cache` in `save()`.
- `is_instance_level`, `slug_config`, and the serialized `category` are computed on read; none of them is a stored column.

## Methods & save behaviour

### `save()` side effects

`save()` calls `set_names_cache()` before it writes the record:

1. `names_cache` is reset to `"<name> "`.
2. The `name` of each entry in `names` is appended, separated by spaces.
3. `super().save()` writes the record.

`names_cache` is platform-maintained: write `name` and `names` instead.

### Slug prefixing

`ProductKnowledgeViewSet.recalculate_slug()` runs in `perform_create` and `perform_update`. It stores `f-<facility external_id>-<slug_value>` for a facility record and `i-<slug_value>` for an instance-level record. `SlugBaseModel` has no `save()` of its own.

## API integration notes

### Endpoints

The API is registered at `/api/v1/product_knowledge/`, not nested under a facility. Records are addressed by `slug`, the full prefixed slug.

| Method and path | Action | Notes |
| --- | --- | --- |
| `GET /api/v1/product_knowledge/` | list | See filters and scoping below |
| `POST /api/v1/product_knowledge/` | create | Body: `ProductKnowledgeWriteSpec` |
| `GET /api/v1/product_knowledge/<slug>/` | retrieve | Returns `ProductKnowledgeReadSpec` |
| `PUT /api/v1/product_knowledge/<slug>/` | update | Body: `ProductKnowledgeUpdateSpec`. The UI sends `PUT` |
| `POST /api/v1/product_knowledge/upsert/` | upsert | Body: a `datapoints` list. A datapoint with `id` (the slug) updates that record; one without `id` creates a record. If any datapoint fails, the batch is rolled back and the response is 400 with the per-datapoint results |
| `GET /api/v1/product_knowledge/favorite_lists/` | favorites | The caller's favorite list names |
| `POST /api/v1/product_knowledge/<slug>/add_favorite/` | favorites | Body: optional `favorite_list` |
| `POST /api/v1/product_knowledge/<slug>/remove_favorite/` | favorites | Body: optional `favorite_list` |

There is no delete endpoint. The UI's "Delete" action sends a `PUT` that sets `status` to `retired`.

### Filters and ordering

| Parameter | Behaviour |
| --- | --- |
| `facility` | Scopes the list to one facility. See scoping below |
| `include_instance` | With `facility`: `true` adds instance-level records |
| `category` | A category slug, looked up in the same facility. With `include_children=true`, records in descendant categories are also returned |
| `status`, `product_type`, `alternate_identifier` | Exact match, case-insensitive |
| `name`, `alternate_names` | Trigram similarity above 0.1 on `name` or `names_cache`, ordered by similarity |
| `facility_is_null` | Null filter on `facility` |
| `ordering` | `created_date` or `modified_date` |

### Scoping and authorization

- List with `facility`: requires `can_read_product_knowledge` in any organization of that facility. Returns that facility's records, plus instance-level records when `include_instance=true`.
- List without `facility`: returns only instance-level records, with no permission check.
- Retrieve a facility record: requires `can_read_product_knowledge` in any organization of its facility; otherwise 403 "Cannot read product knowledge". Retrieving an instance-level record has no permission check.
- Create a facility record: requires `can_write_product_knowledge` in the facility's root organization (named "Administration"); otherwise 403 "Cannot create product knowledge". A role holding the permission in another department of the facility is refused.
- Update a facility record: requires `can_write_product_knowledge` in the root organization of the record's facility; otherwise 403 "Cannot update product knowledge".
- Instance-level records cannot be created or updated through facility permissions.
- Only facility-organization memberships count; governance-organization memberships are not consulted.
- The frontend's list calls send `include_instance=true` by default, so pickers that do not override it also list instance-level records.

| Permission | Display name | Checked in | Default roles |
| --- | --- | --- | --- |
| `can_write_product_knowledge` | Can Create Product Knowledge on Facility | The facility's root organization | Facility Admin |
| `can_read_product_knowledge` | Can Read Product Knowledge | Any organization of the facility | Facility Admin, Administrator, Staff, Doctor, Nurse, Volunteer, Pharmacist |

Authorization reads role permissions from the database. Each permission sync rewrites the default roles from code; custom roles can also hold these permissions.

### UI notes

- The UI labels `alternate_identifier` "HSN Code".
- The UI creates records only inside a category with no subcategories, and always sends the current `facility`.
- The 3.1 UI form has no fields for `ingredients`, `nutrients`, or `drug_characteristic`.
- The UI's create form opens with the `definitional` block added, and requires `dosage_form` until the user removes the block.
