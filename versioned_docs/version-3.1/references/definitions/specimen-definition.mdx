# Specimen Definition

Technical reference for the `SpecimenDefinition` module in Care EMR. For the plain-language overview, see the [Specimen Definition concept](../../concepts/definitions/specimen-definition.mdx).

A `SpecimenDefinition` is a facility-scoped template for one kind of specimen: the specimen type to collect, the patient preparation, a collection template, and the container and testing detail. An [Activity Definition](activity-definition.mdx) lists specimen definitions of its own facility in `specimen_requirements`, and a [Service Request](../clinical/service-request.mdx) creates [Specimens](../clinical/specimen.mdx) from specimen definitions of the same facility.

When a specimen is created from a definition, the backend sets `status = available`, copies `type_collected` into `specimen_type`, and links the definition. It does not copy the collection template; the frontend pre-fills `method`, `body_site` and `quantity` from it in the specimen collection form.

The Django model is only the storage layer: `type_collected`, `patient_preparation`, `collection` and `type_tested` are `JSONField`s. Their structure, value-set bindings and read/write schemas live in the Pydantic resource specs below.

## Models

| Model | Purpose |
| --- | --- |
| `SpecimenDefinition` | Reusable, facility-scoped definition of one kind of specimen: type collected, patient preparation, collection template, and type tested (container and testing detail) |

`SpecimenDefinition` extends [`SlugBaseModel`](../foundation/base-model.mdx), which sets `FACILITY_SCOPED = True` and adds slug helpers. `SlugBaseModel` builds on `EMRBaseModel` (`history`, `meta`, `created_by`, `updated_by`) and `BaseModel` (`external_id`, `created_date`, `modified_date`, and soft delete through `deleted`).

### Collection & testing detail (JSON fields)

The model stores these as raw JSON; the spec defines their shape and value-set bindings. See [Nested JSON shapes](#nested-json-shapes).

| Field | Model type | Spec type | Notes |
| --- | --- | --- | --- |
| `type_collected` | `JSONField` (`null=True`, `blank=True`) | `Coding` bound to **Specimen Type Code** | Required on write. See [value sets](#bound-value-sets) |
| `patient_preparation` | `JSONField` (`default=list`) | `list[Coding]` bound to **Prepare Patient Prior Specimen Code** | Defaults to `[]` |

## Resource specs (API schema)

All specs build on `EMRResource`. `__exclude__ = ["facility"]` keeps `facility` out of both directions. The ViewSet uses `pydantic_model = SpecimenDefinitionWriteSpec` for create and update, and `pydantic_read_model = SpecimenDefinitionReadSpec` for list and retrieve.

| Spec class | Role | Fields / behaviour |
| --- | --- | --- |
| `BaseSpecimenDefinitionSpec` | shared base | `id`, `title`, `derived_from_uri`, `status`, `description`, `type_collected`, `patient_preparation`, `collection`, `type_tested`. Holds the value-set bindings and the nested shapes |
| `SpecimenDefinitionWriteSpec` | write · create & update | Base fields **plus** `slug_value: SlugType`. `perform_extra_deserialization` copies `slug_value` into `obj.slug`; the ViewSet then qualifies it. `facility`, `version` and the stored `slug` are never client-supplied |
| `SpecimenDefinitionReadSpec` | read · list & retrieve | Base fields **plus** `version: int?`, `slug: str`, `slug_config: dict`. `perform_extra_serialization` sets `id = obj.external_id` and `slug_config = obj.parse_slug(obj.slug)`, which gives `{ facility, slug_value }` |

Nested specs used by the schemas: `CollectionTemplateSpec`, `TypeTestedSpec`, `ContainerSpec`, `MinimumVolumeSpec`, `QuantitySpec`, `DurationSpec`, `RangeSpec`, `HandlingSpec` (see [Nested JSON shapes](#nested-json-shapes)).

### Validation rules

- `slug_value` (`SlugType`): string, 5–50 characters, matching `^[a-zA-Z0-9][a-zA-Z0-9_-]*[a-zA-Z0-9]$`.
- Coded fields `type_collected`, `patient_preparation[*]`, `collection.code`, `collection.method`, `collection.body_site` and `type_tested.container.cap`: `ValueSetBoundCoding` checks each `code` against its bound value set and rejects unknown codes.
- `MinimumVolumeSpec`: `quantity` and `string` are mutually exclusive; supplying both raises "Only one of quantity or string should be provided".
- `QuantitySpec` and `DurationSpec` `value`: `Decimal`, `max_digits=20`, `decimal_places=0` (whole numbers). This covers `collection.quantity`, `container.capacity`, `container.minimum_volume.quantity` and `retention_time`. The 3.1 form accepts decimals for capacity, minimum volume and retention time, and rounds them to the accounting precision before sending.
- Slug uniqueness (ViewSet `validate_data`): the qualified `f-<facility>-<slug_value>` must not match any other specimen definition (case-insensitive), else "Specimen Definition with this slug already exists.". On update, the check uses the record's own facility and excludes the record itself.

### Bound value sets

| Field | Value set | Slug | Composition |
| --- | --- | --- | --- |
| `type_collected` | Specimen Type Code | `system-specimen_type-code` | HL7 v2-0487 (version 2.0.0), whole code system |
| `patient_preparation[*]` | Prepare Patient Prior Specimen Code | `system-prepare_patient_prior_specimen_code` | SNOMED CT, `is-a 703763000` |
| `collection.code` | Specimen Collection Code | `system-specimen_collection_code` | SNOMED CT, ten listed concepts: aspiration, biopsy, puncture, excision, scraping, clean-catch urine, timed urine, catheterized urine, coughed sputum, finger-prick sampling |
| `collection.method` | Collection Method | `system-collection-method-code` | SNOMED CT, the same ten concepts as Specimen Collection Code |
| `collection.body_site` | Body Site | `system-body-site-observation` | SNOMED CT: a listed set of concepts plus every concept under `442083009`; shared with observation definitions |
| `type_tested.container.cap` | Container Cap | `system-container_cap-code` | HL7 `container-cap` code system |

## Methods & save behaviour

`SpecimenDefinition` overrides no `save()` or `delete()` and defines no methods. Slug helpers, audit fields and soft delete come from [`SlugBaseModel`](../foundation/base-model.mdx) and its bases. The side effects below live in the resource spec and the ViewSet, not the model:

- **Slug qualification (write).** Clients send a bare `slug_value`. `SpecimenDefinitionWriteSpec.perform_extra_deserialization` sets `obj.slug = slug_value`; then `perform_create` and `perform_update` rewrite it with `SpecimenDefinition.calculate_slug_from_facility(facility.external_id, slug)` to `f-<facility_external_id>-<slug_value>`.
- **Facility binding (create).** `perform_create` sets `instance.facility` from the `facility_external_id` URL kwarg before saving.
- **Slug decomposition (read).** `SpecimenDefinitionReadSpec.perform_extra_serialization` exposes `slug_config = obj.parse_slug(obj.slug)`, which splits the stored slug into `{ facility, slug_value }`.
- **Specimen creation.** `convert_sd_to_specimen` ([`specimen.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/specimen_definition/specimen.py)) builds a [`Specimen`](../clinical/specimen.mdx) with `status="available"`, `specimen_type = definition.type_collected` and `specimen_definition = <definition>`. It does not copy the collection template.

## API integration notes

- **Endpoints are facility-scoped.** `/api/v1/facility/{facility_external_id}/specimen_definition/` supports list, create, retrieve, update and upsert, with `lookup_field = "slug"`. There is no delete.
- **Read authorization.** Every action that reads the queryset (list, retrieve, and update through `get_object`) calls `can_list_facility_specimen_definition` for the facility in the URL. It checks `can_read_specimen_definition` ("Can Read Specimen Definition") in any organization of that facility.
- **Write authorization.** Create and update call `can_write_facility_specimen_definition` for the facility in the URL. It checks `can_write_specimen_definition` ("Can Create Specimen Definition on Facility") in the facility's root organization only; a role in a sub-organization does not pass. An update therefore needs both permissions. A failed check returns `403` "Access Denied to Specimen Definition".
- **Default roles.** `can_write_specimen_definition`: Facility Admin. `can_read_specimen_definition`: Facility Admin, Administrator, Staff, Doctor, Nurse, Volunteer, Pharmacist. Each sync rewrites the system roles from code; custom roles can hold either permission.
- **Facility scope.** The queryset is filtered to the facility in the URL.
- **Filtering / ordering.** `status` (iexact) and `title` (icontains) filters; ordering by `created_date` or `modified_date`.
- **Write payload** (`SpecimenDefinitionWriteSpec`): send `slug_value`, `title`, `status`, `description`, optional `derived_from_uri`, `type_collected` and `patient_preparation` as `Coding` objects, `collection` as a `CollectionTemplateSpec`, and `type_tested`. Do not send `facility`, `version` or the qualified `slug`.
- **Read payload** (`SpecimenDefinitionReadSpec`): adds `id` (the `external_id`), `version`, the qualified `slug` and `slug_config`.
- **Frontend behaviour.** The 3.1 frontend calls list, retrieve, create and update only. Its **Delete** action sends a full update with `status` set to `retired`. On save it sends an empty collection as `{}`, drops empty patient preparation rows and leaves out an empty container.
- **Handling and the form.** The 3.1 form has no fields for `type_tested.handling`. Its schema drops keys it does not know, and it sends `type_tested` as one object.
