# Questionnaire

Technical reference for the `Questionnaire` module in Care EMR. For what a questionnaire is in the product, see the [Questionnaire concept](../../concepts/definitions/questionnaire.mdx).

**Source (model):** [`care/emr/models/questionnaire.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/models/questionnaire.py)

**Source (specs):** [`resources/questionnaire/spec.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/questionnaire/spec.py) · [`resources/questionnaire/utils.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/questionnaire/utils.py) · [`resources/questionnaire/questionnaire_organization.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/questionnaire/questionnaire_organization.py) · [`resources/questionnaire_response/spec.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/questionnaire_response/spec.py) · [`resources/form_submission/spec.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/form_submission/spec.py)

**Source (API):** [`api/viewsets/questionnaire/questionnaire.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/api/viewsets/questionnaire/questionnaire.py) · [`security/authorization/questionnaire.py`](https://github.com/ohcnetwork/care/blob/develop/care/security/authorization/questionnaire.py)

The Django model is only the storage layer. `questions` is an opaque `JSONField` there; the Pydantic specs define its recursive `Question` shape, the enums, the validation, and the split between the create, update, and read contracts.

A questionnaire has a scope (`auth_context`) and a revision chain. Each update that changes the questions copies the old row as a past revision, so a response can be read against the questions it was answered with.

## Models

| Model | Purpose |
| --- | --- |
| `Questionnaire` | A form definition: questions, subject type, status, scope, and revision chain |
| `FormSubmission` | A submission record for a questionnaire, a patient, and an optional encounter, with a status and a response dump |
| `QuestionnaireResponse` | The stored answers for a subject, with the questionnaire revision they were answered with |
| `QuestionnaireOrganization` | Links an instance questionnaire to an instance `Organization` |
| `QuestionnaireFacilityOrganization` | Links a facility questionnaire to a `FacilityOrganization` (department) |
| `QuestionnaireResponseTemplate` | A reusable template of answers (`template_data`) for a questionnaire; see the [Questionnaire Response Template reference](./questionnaire-response-template.mdx) |

All six extend [`EMRBaseModel`](../foundation/base-model.mdx).

#### Slug uniqueness

Slugs are unique per scope among current rows (rows with no `latest_revision`), compared case-insensitively. The viewset checks this before it saves and raises "Questionnaire with this slug already exists."; four partial unique constraints enforce it in the database for rows that are not deleted and have no `latest_revision`. The check runs only when a slug is given.

| Scope | Unique within | Constraint |
| --- | --- | --- |
| `instance` | All instance questionnaires | `unique_questionnaire_slug_instance` |
| `facility` | The facility | `unique_questionnaire_slug_facility` |
| `facility_organization` | The facility organization | `unique_questionnaire_slug_facility_organization` |
| `user` | The facility and the creator | `unique_questionnaire_slug_user` |

Past revisions keep the slug of the row they were copied from.

- `choice` and `quantity` questions must have `answer_option` or `answer_value_set`.

## Methods & save behaviour

### Revisions on update

`QuestionnaireUpdateSpec.perform_extra_deserialization` hashes the incoming questions and compares the hash with the stored `questions_hash`. If they differ, it saves a copy of the old row with a new `external_id` and `latest_revision` set to the current row, increments `internal_revision`, and stores the new hash. If they match, no revision is made, so an update of the title, slug, description, or status alone keeps the revision.

A past revision cannot be updated ("This Questionnaire is a past revision, please update the latest revision") or submitted to.

### Update lock

`handle_update` takes a `QuestionnaireLock` on the row. A concurrent update fails with "Questionnaire update failed, try again after a while".

### Create

`QuestionnaireCreateSpec.perform_extra_deserialization` resolves the facility (or the facility organization and its facility), sets `questions_hash`, and for `facility_organization` scope sets `internal_organization_cache`. After the save, the viewset calls `sync_facility_org_cache()`.

### Access cache sync

| Method | Scope | Result |
| --- | --- | --- |
| `sync_facility_org_cache()` | `facility` | `internal_organization_cache` = the facility's root organization, each linked department, and each linked department's parents. Called after create and by `set_facility_organizations` |
| `sync_facility_org_cache()` | `facility_organization` | `internal_organization_cache` = the organization and its parents |
| `sync_org_cache()` | `instance` | `organization_cache` = each linked `Organization` and its parents. Called by `set_organizations` |

Each method de-duplicates the ids and saves only its cache field.

### `Questionnaire.get_questions_by_id()`

Walks the `questions` tree, recursing into nested `questions`, and returns a `{ str(question_id): question }` dict. The result is memoized on the instance in `_questions_by_id_cache`. If `questions` is not a list, it returns an empty dict.

### `QuestionnaireResponse.resolved_questionnaire` and `render_responses()`

`resolved_questionnaire` returns the linked questionnaire when the response's `revision` equals its `internal_revision`; otherwise it returns the past revision whose `latest_revision` is that questionnaire and whose `internal_revision` equals the response's `revision`.

`render_responses()` pairs each stored answer with its question from that revision. It skips answers whose `question_id` is not in that revision, and returns an empty list when there are no responses or no questionnaire.

### Submission handling

`submit` and `handle_response()` in `utils.py` run these steps:

1. Refuse referral questionnaires and past revisions.
2. For an encounter questionnaire, require an encounter of the given patient, refuse an encounter from another facility when the questionnaire has a facility, and check the encounter submit permission. For other subject types, refuse an encounter and check the patient submit permission.
3. Refuse the submission if the questionnaire `status` is not `active` (`questionnaire_inactive`) or if it has no answers (`questionnaire_empty`).
4. Drop questions whose `enable_when` conditions fail; an answer to a dropped question is an `enable_when_failed` error. A condition whose answer is an object compares coding system and code.
5. Validate each answer: `required`, the type checks in [QuestionType](#questiontype-values), value-set membership, and `quantity` units. Any failure aborts with an `errors` payload.
6. Refuse a patient questionnaire that is not instance-level, then resolve the encounter and the patient.
7. Create the `QuestionnaireResponse` with `responses` and `cleaned_response`, and store the questionnaire's `internal_revision` in `revision`.
8. When an encounter is present, bulk-create the derived [Observations](../clinical/observation.mdx), linked to the response.
9. If `form_submission` is given, it must be a draft for the same questionnaire and patient with no response yet; link the response to it.
10. Evaluate the questionnaire's `actions` with the patient or encounter questionnaire context, and return the result under `_actions`.

`submit_resource` serves location, device, and facility questionnaires. It checks the resource permission and that the resource's facility matches the questionnaire's facility, then runs the same answer validation and writes a `FacilityResourceQuestionnaireResponse` and `FacilityResourceObservation` rows instead.

## API integration notes

- Routes: `/api/v1/questionnaire/` (list, create) and `/api/v1/questionnaire/<id>/` (retrieve, update, delete), plus `upsert`, the [favorites](../platform/favorites.mdx) actions (`favorite_lists`, `add_favorite`, `remove_favorite`), and the detail actions `submit`, `submit_resource`, `get_facility_organizations`, `set_facility_organizations`, `get_organizations`, and `set_organizations`.
- Questionnaires are looked up by `external_id` (UUID), not by slug.
- List filters: `title` (contains, case-insensitive), `subject_type` (multi-select), `auth_context` (exact, case-insensitive), `facility`, `facility_isnull`, `status` (exact, case-insensitive), `parent_revision`, `facility_or_instance`, `slug` (exact, case-insensitive). Without `parent_revision`, the list returns only current rows; with it, the past revisions of that questionnaire. `facility_or_instance` returns the facility's rows plus rows with no facility.
- The list returns the questionnaires whose `organization_cache` overlaps an instance organization where the caller holds a role with "Can Read Questionnaires", or whose `internal_organization_cache` overlaps such a facility organization, plus the caller's own `user` questionnaires. Other actions run per-object checks instead.
- `facility` scope: retrieve needs "Can Read Questionnaires" in a facility organization listed in `internal_organization_cache`; create, update, and delete need "Can Create/Update Questionnaires" in the facility's root organization.
- `facility_organization` scope: read or write permission in that organization or one of its parents. `user` scope: the permission in any organization of the facility, and only the creator can update or delete.
- `instance` scope: no facility permission allows create, update, delete, or organization changes.
- On create and update, each action instruction must be authorized for the caller; an unknown or unauthorized instruction is a validation error.
- `get_facility_organizations` and `set_facility_organizations` work only for `facility` questionnaires, and both run the update authorization, so reading the linked departments also needs write access. `set_facility_organizations` takes `{ facility_organizations: list[UUID4] }` and replaces every link; each department must belong to the questionnaire's facility (404 otherwise).
- `get_organizations` and `set_organizations` work only for `instance` questionnaires.
- Delete is a soft delete with the update authorization. The frontend does not call it.
- Server-maintained, and in no write spec: `internal_revision`, `latest_revision`, `questions_hash`, `organization_cache`, `internal_organization_cache`, and `QuestionnaireResponse.revision`.
- Submitting validates answers server-side and, when an encounter is present, creates [Observations](../clinical/observation.mdx). `QuestionnaireResponseUpdate` changes only the response status, for example to `entered_in_error`.
