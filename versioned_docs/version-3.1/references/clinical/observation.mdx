# Observation

Technical reference for the `Observation` module in Care EMR. For the plain-language view, see the [Observation concept](../../concepts/clinical/observation.mdx).

**Source:**

- Model: [`care/emr/models/observation.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/models/observation.py)
- Specs: [`care/emr/resources/observation/spec.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/observation/spec.py) · [`valueset.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/observation/valueset.py)
- Viewset: [`care/emr/api/viewsets/observation.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/api/viewsets/observation.py) · read and write checks in [`encounter_authz_base.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/api/viewsets/encounter_authz_base.py)
- Other write paths: [`care/emr/resources/questionnaire/utils.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/resources/questionnaire/utils.py) (questionnaire submission) · [`care/emr/api/viewsets/diagnostic_report.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/api/viewsets/diagnostic_report.py) (test results) · [`compute_observation_interpretation.py`](https://github.com/ohcnetwork/care/blob/develop/care/emr/utils/compute_observation_interpretation.py)

An observation is one recorded result about a patient in an encounter: a value or a coded answer for one code at one effective time.

The Django model is the storage layer. It keeps the codes, the value, the reference ranges, the interpretation and the components as JSON fields.

The Pydantic resource specs give those fields their shape. They also define the enums, the bound value sets, and the separate read and write schemas.

Three paths write observations: questionnaire submission, test results on a diagnostic report (`upsert_observations`), and direct create on the observation API. Each path sets different fields. See "Methods & save behaviour".

The observation API has no update. A `DELETE` does not remove the record: it marks the observation entered in error.

## Models

| Model | Purpose |
| --- | --- |
| `Observation` | One recorded result about a patient, linked to one encounter: a value or coded answer for one code at one effective time |

`Observation` extends [`EMRBaseModel`](../foundation/base-model.mdx). Through it, each observation also has `history` and `meta` JSON fields and `created_by` / `updated_by` user links.

The API identifies an observation by its `external_id`, which read responses return as `id`.

## Nested JSON shapes

### `Coding`

`main_code`, `category`, `body_site`, `method`, `value.unit`, `value.coding` and `component[].code` are codings. Care rejects any key that is not listed.

```text
Coding {
  system:  str | null
  version: str | null
  code:    str            required
  display: str | null
}
```

`code` has no minimum length, so an empty code (`""`) is accepted.

### `alternate_coding`: `CodeableConcept`

The `text` key must be present, but it may be `null`. Care rejects any key that is not listed.

```text
CodeableConcept {
  id:     str | null
  coding: Coding[] | null
  text:   str | null      key required
}
```

### `value`: `QuestionnaireSubmitResultValue`

All three parts are optional. `value` is text, `unit` is the coding of a quantity's unit, and `coding` is the coding of a coded answer.

```text
QuestionnaireSubmitResultValue {
  value:  str | null
  unit:   Coding | null
  coding: Coding | null
}
```

How each write path fills `value`:

- Questionnaire, choice answer with a coding: `coding` holds the answer's coding.
- Questionnaire, quantity answer with a coding: `unit` is the question's unit, `value` the entered number, and `coding` the answer's coding.
- The Care frontend sends the unit picked in the questionnaire as the answer's coding. So the picked unit is kept only in `value.coding`, and `value.unit` is always the question's unit.
- Questionnaire, any other answer: `value` holds the entered value, plus the question's `unit` when the question has one.
- Questionnaire, group: an empty object.
- Questionnaire, answer with several values: one observation, with the last value only.
- Test results from the Care frontend: the unit is the observation definition's unit.

### `performer`: `Performer`

```text
Performer {
  type: PerformerType     related_person | user
  id:   str
}
```

A performer has a `type` and an `id`.

### `reference_range[]`: `ReferenceRange`

The spec types a reference range as follows.

```text
ReferenceRange {
  min:            float | null
  max:            float | null
  unit:           str | null
  interpretation: str             required
  value:          str | null
}
```

The reference ranges that Care computes for test results are the numeric ranges of the matching qualified range. Each stored entry therefore carries an interpretation object, not text.

### `interpretation`: computed interpretation object

The shared spec types `interpretation` as a free object. The interpretation that Care computes from an observation definition has this shape.

```text
Interpretation {
  display:   str            required
  icon:      optional
  color:     optional
  highlight: bool | null    default false
  code:      optional
}
```

The built-in coded interpretations are `{"display": "Normal"}`, `{"display": "Critical"}` and `{"display": "Abnormal"}`.

### `component[]`: `Component`

```text
Component {
  value:           QuestionnaireSubmitResultValue   required
  interpretation:  str | dict                       default {}
  reference_range: ReferenceRange[]                 default []
  code:            Coding | null                    default null
  note:            str                              default ""
}
```

The spec defines a component as above. A questionnaire component holds the sub-question's code, value and note.

## Related models

`Observation` links to other models as follows. `parent` points to another observation and is not a foreign key. Deleting the patient row deletes its observations (`CASCADE`).

```text
Observation
  patient                → FK emr.Patient                (CASCADE)
  encounter              → FK emr.Encounter              (CASCADE, required)
  data_entered_by        → FK users.User                 (CASCADE, nullable)
  questionnaire_response → FK emr.QuestionnaireResponse  (CASCADE, nullable)
  diagnostic_report      → FK emr.DiagnosticReport       (CASCADE, nullable)
  observation_definition → FK emr.ObservationDefinition  (CASCADE, nullable)
  parent                 → UUIDField: id of another Observation (not a foreign key)
```

Observations about locations, devices and facilities are a separate model, `FacilityResourceObservation`, tied to a facility. This page does not cover it.

## Resource specs (API schema)

`ObservationCreateSpec` extends `EMRResource` directly. `ObservationUpdateSpec`, `ObservationSpec` and `ObservationReadSpec` extend the shared `BaseObservationSpec`, and `ObservationRetrieveSpec` extends `ObservationReadSpec`.

| Spec | Role | Notes |
| --- | --- | --- |
| `BaseObservationSpec` | shared base | `status` required. `subject_type` default `encounter`. `body_site` and `method` bound to value sets. `interpretation` a free object, default `{}`. `parent` and `questionnaire_response` optional UUIDs. `component` default `[]` |
| `ObservationCreateSpec` | write · create (`POST`) | "An observation entered independently of a questionnaire or diagnostic report". Rejects any field it does not list |
| `ObservationUpdateSpec` | write · `upsert_observations` | The shared spec with `effective_datetime` and `value` optional. `status` stays required |
| `ObservationSpec` | internal · questionnaire submission | Adds `data_entered_by_id`, `created_by_id` and `updated_by_id`, and keeps the observation ID generated during submission |
| `ObservationReadSpec` | read · list | Adds `is_random`, `created_by`, `updated_by` and `data_entered_by` |
| `ObservationRetrieveSpec` | read · detail | Extends the read spec with `observation_definition`, when one is linked |

### Create: `ObservationCreateSpec`

The body of `POST /api/v1/patient/{patient_id}/observation/`.

```text
{
  "encounter":          UUID,                             required
  "status":             "final",                          optional; default "final"; no other value
  "main_code":          Coding,                           required; not bound to a value set
  "effective_datetime": datetime with timezone,           required
  "value_type":         QuestionType,                     required
  "value":              QuestionnaireSubmitResultValue,   required
  "category":           Coding | null,                    optional
  "alternate_coding":   CodeableConcept,                  optional
  "performer":          Performer,                        optional
  "note":               str,                              optional
  "body_site":          Coding in system-body-site-observation,   optional
  "method":             Coding in system-collection-method,       optional
  "component":          Component[],                      optional; default []
}
```

- Any other field is rejected with HTTP 400. This includes `id`, `questionnaire_response`, `diagnostic_report`, `parent`, `created_by_id`, `data_entered_by_id`, `is_random` and `meta`.
- The create spec has no `reference_range`, `interpretation` or `observation_definition`.
- Care takes the patient from the encounter, sets `subject_type` to `encounter`, and sets `subject_id` to the encounter's ID.
- Care sets `data_entered_by`, `created_by` and `updated_by` to the signed-in user.
- The response is the full saved observation.

### Read: `ObservationReadSpec` and `ObservationRetrieveSpec`

- `id` is the observation's `external_id`.
- `is_random` tells whether the observation was entered on its own, not through a questionnaire or a diagnostic report.
- `created_by` and `updated_by` are user objects. `data_entered_by` is a user object when it is set.
- `encounter` and `questionnaire_response` are always `null` in read responses, to avoid extra queries.
- Retrieve also returns the linked observation definition as `observation_definition`.

### Deserialization

Generic deserialization never writes a foreign key, `id` or `external_id` from a request body. Care sets those fields itself on each path.

## Methods & save behaviour

### `is_random`

`is_random` is a model property. It is true when the observation has neither a questionnaire response nor a diagnostic report. Only random observations can be marked entered in error with `DELETE`.

### Write path 1: questionnaire submission

Questionnaire answers are submitted with `POST /api/v1/questionnaire/{questionnaire_id}/submit/`. Care builds the observations with the internal `ObservationSpec`.

- Observations are stored only when the submission has an encounter. A patient questionnaire saves the questionnaire response and no observations.
- A question that is not a group produces an observation only if the question has a code.
- Each observation has status `final` and takes `value_type` from the question type.
- `main_code` is the question's code. A stored question has no `category` key, so questionnaire observations have no category.
- `effective_datetime` is the moment of submission. A time taken on the answer is not stored.
- The note of the answer is copied. Body site and method are not stored.
- `subject_type` is the questionnaire's subject type. The submitting user is recorded as `data_entered_by`, `created_by` and `updated_by`.
- Each observation is linked to the questionnaire response, the patient and the encounter. `subject_id` is the submission's resource ID.
- No observation definition, reference range or interpretation is set.
- A group question gives a group observation: `value_type` `group`, an empty `value`, and the submission time.
- In an ordinary group, each answer inside gives a separate observation whose `parent` is the group observation's ID. Care keeps the group observation only if it has at least one child.
- A group marked as component gives one observation, with the answers as its components. A repeating group gives one such observation per repetition.
- Marking the questionnaire response entered in error marks every observation created from it entered in error.

### Write path 2: test results on a diagnostic report (`upsert_observations`)

Results are written with `POST /api/v1/patient/{patient_id}/diagnostic_report/{id}/upsert_observations/`. It creates observations from an observation definition or from scratch, or updates existing ones.

Each item has an `observation` body (`ObservationUpdateSpec`, `status` required). It also names an observation definition by slug (`observation_definition`), an existing observation (`observation_id`), or neither for a new observation.

- The call is refused on a final report: "Cannot update observations for a final diagnostic report".
- After that check, Care runs the diagnostic-report write check. It does not check the encounter's status or the service request's status.
- With a definition slug, Care looks up the definition in the report's facility and links it to the new observation. The new observation starts as `final`, with the definition's category and code.
- With `observation_id`, the observation must belong to that report. The fields sent, `status` included, overwrite the stored ones.
- So this path can set an existing observation to `amended` or `entered_in_error`.
- Every observation saved here gets the report's encounter and patient, the report link, and `subject_type` `encounter`. Care sets `updated_by`; it does not set `data_entered_by`.
- When the observation is linked to a definition, Care computes its interpretation and reference ranges before saving. See "Interpretation and reference ranges" below.
- `ObservationUpdateSpec` makes `value` optional, but the `value` column has no default and is not nullable.
- Opening the report returns all its observations in any status, `entered_in_error` included, each with its definition.

The Care frontend sends each result with status `final`, or `entered_in_error` when the user removes it. It never sends `amended`. It sends the moment of saving as `effective_datetime`.

Each **Save Results** sends every saved result of the report again, changed or not. So each one gets the new save time as its effective time.

### Write path 3: direct create

`POST /api/v1/patient/{patient_id}/observation/` creates an observation from `ObservationCreateSpec`. See "Create: `ObservationCreateSpec`" above for the body and the fields that Care sets.

No screen of the Care frontend creates an observation directly or sends `DELETE`. Its observation API has only list, analyse and `upsert_observations`.

### Interpretation and reference ranges

Care computes these only for test results linked to an observation definition. Questionnaire observations and direct creates get none.

- Care evaluates the definition's qualified ranges in the context of the observation's patient and encounter.
- The result sets `interpretation` and `reference_range`. When nothing matches, Care clears both.
- Care uses the first qualified range whose conditions all hold. Conditions can test Patient Age, Patient Gender, Patient Tag, Encounter Class and Encounter Tag.
- Numeric value: it must be between `min` and `max`, both included; a missing bound is open. Care uses the matching range's interpretation and stores all the rule's ranges as the reference range.
- A coded value against numeric ranges raises "Coding not supported".
- Coded value: Care checks the coding against the rule's normal, then critical, then abnormal value set, which give "Normal", "Critical" or "Abnormal". Then it checks each custom value set interpretation.
- If no range or value set matches, Care uses the rule's default interpretation when it has one.
- Each component whose code matches a component of the definition gets its own interpretation and reference ranges.

### Marking entered in error

- `DELETE` sets `status` to `entered_in_error` and records the user as `updated_by`. It does not remove or soft-delete the observation.
- The value, the author and the data-entry user stay. Repeating the request still returns HTTP 204.
- Only random observations can be marked this way. Others fail with "Only random observations can be marked as entered in error".
- Questionnaire observations: mark the questionnaire response entered in error, which marks all its observations. By default this is possible for 120 minutes after the response is created.
- Test results: send the observation with status `entered_in_error` to `upsert_observations`.
- The observation API has no hard delete and no update.

## API integration notes

### Routes

All routes are under `/api/v1/`. Observation routes are nested under the patient. Every request needs a signed-in user.

| Action | Method and path | Body | Response |
| --- | --- | --- | --- |
| List | `GET /api/v1/patient/{patient_id}/observation/` | None | `count` and `results` |
| Retrieve | `GET /api/v1/patient/{patient_id}/observation/{id}/` | None | The observation, with its observation definition when one is linked |
| Create | `POST /api/v1/patient/{patient_id}/observation/` | `ObservationCreateSpec` | The saved observation |
| Update | `PUT` or `PATCH /api/v1/patient/{patient_id}/observation/{id}/` | None | HTTP 405 |
| Mark entered in error | `DELETE /api/v1/patient/{patient_id}/observation/{id}/` | None | HTTP 204, no body |
| Analyse | `POST /api/v1/patient/{patient_id}/observation/analyse/` | `codes`, `page_size` | `results`: one entry per code |
| Test results | `POST /api/v1/patient/{patient_id}/diagnostic_report/{id}/upsert_observations/` | Items as described above | See "Write path 2" |
| Questionnaire submission | `POST /api/v1/questionnaire/{questionnaire_id}/submit/` | The questionnaire answers | See "Write path 1" |

`{id}` is the observation's `id` as read responses return it.

### List filters, ordering and pages

| Query parameter | Effect |
| --- | --- |
| `encounter` | Encounter external ID. Returns only that encounter's observations. Without patient-level access, the list needs it (see "Authorization") |
| `codes` | Comma-separated codes. Matches the code of `main_code`, not its system. An empty value applies no filter |
| `ignore_group` | `true` leaves out observations whose `value_type` is `group` |
| `status` | Comma-separated statuses. Without it, the list returns every status, `entered_in_error` included |
| `limit` | Records per page: 14 by default, at most 200 |
| `offset` | Records to skip |

- The list has no ordering parameter and no date-range filter.
- Results are always the most recently modified first, and only for the patient in the URL.

### `analyse`

`analyse` returns the most recently modified observations of several codes in one call.

```text
POST /api/v1/patient/{patient_id}/observation/analyse/
{
  "codes":     Coding[],   1 to 20 codings
  "page_size": int         default 10, at most 30
}
```

- For each coding, Care returns up to `page_size` of the patient's most recently modified observations with that code and system.
- The list's query filters apply first: `encounter`, `status`, `codes` and `ignore_group`.
- The response has `results`, a list with one entry for each requested code. Each entry has the `code` and its `results`.

### Authorization

The table uses these terms.

- "Closed encounter": the encounter's status is `completed`, `cancelled`, `entered_in_error` or `discontinued`.
- "A role on the patient": a role in a facility organization of an open encounter of the patient, or of its current location. It can also come from the patient's geographic organizations, or a direct patient–user association.
- "An organization of the encounter": one of the encounter's facility organizations (its departments), or an organization of its current location.
- The encounter's facility organizations include the organizations it is assigned to, their parents, and the facility's root organization "Administration".
- Where the "Held where" column names organizations, the user must hold a role that carries the permission in one of them.

| Action | Permission (display name, slug) | Held where | Conditions and refusal |
| --- | --- | --- | --- |
| Retrieve | "Can view clinical data about patients" (`can_view_clinical_data`) | A role on the patient | Refusal: "Permission denied to user" |
| List, analyse | "Can view clinical data about patients" (`can_view_clinical_data`) | A role on the patient | If this check fails, Care tries the next row |
| List, analyse, with `?encounter=` | "Can Read encounter related clinical data" (`can_read_encounter_clinical_data`) | An organization of the encounter named in `encounter` | Open and closed encounters alike. Without `encounter`, a user with only this permission gets HTTP 403. Refusal: "Permission denied to user" |
| Create | "Update Encounter related clinical data" (`can_write_encounter_clinical_data`) | An organization of the encounter in the body | Refused for a closed encounter (HTTP 403). Refusal: "You do not have permission to update encounter" |
| Mark entered in error (`DELETE`) | "Update Encounter related clinical data" (`can_write_encounter_clinical_data`) | An organization of the observation's encounter | Refused for a closed encounter. The observation must be random and belong to the patient in the URL. No read check runs |
| Questionnaire submission (encounter questionnaire) | "Can submit questionnaire about patient encounters" (`can_submit_encounter_questionnaire`) | An organization of the encounter | Refused for a closed encounter: "Permission Denied to submit encounter questionnaire". The encounter must belong to the patient ("Encounter is required for this questionnaire"), and to the questionnaire's facility for a facility questionnaire ("Encounter facility does not match questionnaire facility"). The questionnaire must be active ("Questionnaire is inactive") and the latest revision; an empty submission fails ("Empty Questionnaire cannot be submitted") |
| Mark a questionnaire response entered in error | "Can submit questionnaire about patient encounters" (`can_submit_encounter_questionnaire`) | An organization of the encounter | First, the response must be readable: "Can view clinical data about patients" through a role on the patient, or "Can Read encounter related clinical data" in an organization of the encounter; else "You do not have permission to view questionnaire responses". Refused for a closed encounter: "Permission Denied to update encounter questionnaire". Refused when the response is already entered in error, or after the edit window (120 minutes by default): "Questionnaire Response cannot be edited" |
| `upsert_observations` | "Can Create Diagnostic Report on Facility" (`can_write_diagnostic_report`) | An organization of the service request's encounter, or of one of the service request's locations | The report is not final. The encounter's status is not checked. Refusal: HTTP 403, "You do not have permission to write this diagnostic report" |
| Read test results (open the diagnostic report) | "Can Read Diagnostic Report" (`can_read_diagnostic_report`) | The same places as the write check | Refusal: "You do not have permission to read this diagnostic report" |

Default roles per permission:

| Permission (display name) | Slug | Default roles |
| --- | --- | --- |
| Can view clinical data about patients | `can_view_clinical_data` | Staff, Doctor, Nurse, Admin, Facility Admin |
| Can Read encounter related clinical data | `can_read_encounter_clinical_data` | Admin, Doctor, Nurse, Facility Admin |
| Update Encounter related clinical data | `can_write_encounter_clinical_data` | Admin, Doctor, Nurse, Facility Admin |
| Can submit questionnaire about patient encounters | `can_submit_encounter_questionnaire` | Staff, Doctor, Nurse, Admin, Facility Admin |
| Can Create Diagnostic Report on Facility | `can_write_diagnostic_report` | Facility Admin, Admin, Doctor, Nurse |
| Can Read Diagnostic Report | `can_read_diagnostic_report` | Facility Admin, Administrator, Admin, Staff, Doctor, Nurse, Volunteer |

- "Admin" is the facility role. A second role named "Admin" exists only for role organizations.
- Staff does not hold "Can Read encounter related clinical data" or "Update Encounter related clinical data". Staff reads observations only through a role on the patient.
- These role lists are the defaults in code. The roles of an installation can be changed.

### Errors

- A create body with a field that the create spec does not list: HTTP 400.
- An encounter of another patient: "Patient external ID mismatch with encounter's patient". An unknown encounter: not found.
- A `body_site` or `method` code outside its value set: "Code does not exist in the valueset".
- A create in a closed encounter: HTTP 403.
- `PUT` or `PATCH` on an observation: HTTP 405.
- A request without a signed-in user: HTTP 403.

### Other places observations appear

- Referrals: an observation can be attached to a referral as a resource of type `observation`.
- Reading it there needs the patient-level read check ("Can view clinical data about patients"), or the encounter-level read check on the observation's encounter. Otherwise: "Permission denied to read this resource".
- Report templates: a diagnostic report's template can include its observations, with title, value, components, status, effective date and time, interpretation and reference ranges.
- Resource observations (`/api/v1/resource_observation/`) come from location, device and facility questionnaires and need "Can View Resource Responses"; no staff screen reads them.
