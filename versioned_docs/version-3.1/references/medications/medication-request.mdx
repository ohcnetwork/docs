# Medication request

Technical reference for the `MedicationRequest` module in Care EMR. For what a medication request is in the product, see the [Medication request](../../concepts/medications/medication-request.mdx) concept.

A medication request records one medicine ordered for a patient in an encounter. It can belong to a prescription, which groups medication requests of the same encounter, but the link is optional.

The Django model stores `medication` and `dosage_instruction` as JSON columns. The Pydantic resource specs define their shape, the enums, the validation and the read and write schemas. This page covers both layers.

## Models

| Model | Purpose |
| --- | --- |
| `MedicationRequest` | One medicine ordered for a patient within an encounter |
| `MedicationRequestPrescription` | An optional group of medication requests in one encounter (a prescription) |

Both extend [`EMRBaseModel`](../foundation/base-model.mdx). It supplies `external_id`, `created_date`, `modified_date`, the soft-delete flag `deleted`, `created_by`, `updated_by`, `history` and `meta`.

## Bound value sets

Coded fields bind to Care value sets through `ValueSetBoundCoding[<slug>]`. Every write checks the `code` against the value set and refuses a code outside it ("Code does not exist in the valueset").

| Field | Value set slug | SNOMED CT scope |
| --- | --- | --- |
| `medication` | `system-medication` | `<< 763158003` Medicinal product |
| `dosage_instruction[].route` | `system-route` | is-a `284009009` |
| `dosage_instruction[].site` | `system-body-site` | is-a `91723000` |
| `dosage_instruction[].method` | `system-administration-method` | is-a `736665006` |
| `dosage_instruction[].as_needed_for` | `system-as-needed-reason` | is-a `404684003` |
| `dosage_instruction[].additional_instruction` | `system-additional-instruction` | is-a `419492006` |

Care checks codes against the copy of each value set in the database. A deployment can change that copy after it is loaded, so the codes allowed at a deployment can differ from the scope above.

The same directory defines `system-medication-not-given`. No medication spec binds it.

## Related models

### `MedicationRequestPrescription`

A prescription groups medication requests of one encounter. Each request points to at most one prescription through `MedicationRequest.prescription`.

```text
encounter            → FK Encounter (CASCADE)
patient              → FK Patient (CASCADE)
name                 → CharField(100), nullable
note                 → TextField, nullable
prescribed_by        → FK users.User (CASCADE, nullable)
status               → CharField(100), nullable → MedicationRequestPrescriptionStatus
approval_status      → CharField(100), nullable; no spec reads or writes it
alternate_identifier → CharField(100), nullable; set only through create_prescription
tags                 → ArrayField[int], default []
tags_data            → JSONField, default {}; added in the 3.1 release
```

The `unique_alternate_identifier_encounter` constraint keeps `alternate_identifier` unique within an encounter.

`tags_data` holds the expiry of each tag, keyed by the tag id as a string. Care writes the entry when a tag is set with an expiry and removes it when the tag is removed.

```text
tags_data = {
  "<tag id>": { "expiry": "<ISO date-time>" }
}
```

On a read, a rendered tag that has an expiry carries `expiry`, and also `expired: true` after that time.

## Resource specs (API schema)

Resource specs never copy foreign keys automatically. `MedicationRequestResource` also lists `patient`, `encounter`, `requester`, `requested_product` and `prescription` in `__exclude__`, and the extra (de)serialization hooks set them.

| Spec class | Role | Notes |
| --- | --- | --- |
| `MedicationRequestResource` | shared (binding) | Binds the specs to `MedicationRequest` and declares `__exclude__` |
| `MedicationRequestAbstractSpec` | shared (fields) | `status`, `status_reason`, `intent`, `category`, `priority`, `do_not_perform`, `medication`, `dosage_instruction`, `authored_on`, `note`, `dispense_status` |
| `BaseMedicationRequestSpec` | shared | The binding plus the fields plus `id` |
| `MedicationRequestSpec` | write · create | Adds `encounter` (required), `requester`, `requested_product`, `prescription` and `create_prescription`. Holds the validators |
| `MedicationRequestUpdateSpec` | write · update | Only `status` (required), `note` and `dispense_status` |
| `MedicationRequestReadWithoutPrescriptionSpec` | read · embedded | Adds `created_by`, `updated_by`, `created_date`, `modified_date`, `requested_product` (`ProductKnowledgeReadSpec`) and `requester` (`UserSpec`). Used for the medications of an opened prescription |
| `MedicationRequestReadSpec` | read · list and detail | Adds `prescription` (prescription read spec) and the `encounter` id |
| `CreatePrescription` | write · nested | `name` (optional), `note` (optional), `alternate_identifier` (required) |

### Validation (create)

- Sending both `medication` and `requested_product` fails with "Cannot have both medication and requested product". Sending neither fails with "Either medication or requested product is required".
- Sending both `prescription` and `create_prescription` fails with "Cannot have both prescription and create_prescription".
- The `encounter` must exist ("Encounter not found").
- A `requested_product` of another facility fails with "Product not found in facility". A product with no facility passes.
- A `prescription` id must belong to the same encounter, or Care answers 404. Its status is not checked on this path.
- `authored_on` has no validator. Only a `PeriodSpec` (`bounds_period`) requires time-zone-aware date-times.
- The update spec has no status-transition rule. Any status can follow any status.

### Server-side side effects

- `patient` is copied from the encounter, never from the URL or the body.
- With `create_prescription`, Care looks for a prescription with the same `alternate_identifier` in the encounter. A match that is not `active` fails with "Prescription is not active". An `active` match is reused.
- With no match, Care creates an `active` prescription with that identifier, the given `name` and `note`, and the request's `requester` as `prescribed_by`.
- Every create and update also writes a questionnaire response with structured type `medication_request` and submit type `CREATE` or `UPDATE`.

## Methods & save behaviour

The models define no `save()` or `delete()` override. The behaviour below lives in the specs and the viewsets.

- Create runs in this order: validate the body, authorize, build the record (the extra deserialization checks run here), save.
- Fields left at their spec default are not written (`exclude_defaults=True`). So an update cannot clear an optional field by sending `null`.
- An update body loses `id`, `external_id`, `patient` and `encounter` before validation.
- Delete is soft: Care sets `deleted` and keeps the row. The default manager hides deleted rows.
- Dispensing changes `dispense_status`. A dispense with `fully_dispensed` set marks the request `complete` (true) or `partial` (false).
- Cancelling a dispense that has a charge item sets the request to `incomplete` and removes the link from the dispense. Cancelling a dispense order does the same for each of its dispenses.
- A prescription created through the prescription endpoint writes no questionnaire response.

### Authorization

"Clinical write" below means "Update Encounter related clinical data" held in one of the encounter's departments or its current location's departments. The encounter status must not be Completed, Cancelled, Entered in Error or Discontinued.

| Action | Requirement |
| --- | --- |
| Medication request: list | With `?facility=`: "Pharmacist in Care" in any department of that facility. Otherwise "Can view clinical data about patients" on the patient in the URL. Failing that, with `?encounter=`: "Can Read encounter related clinical data" on that encounter. Else 403 "Permission denied to user". The `facility` or `encounter` filter then limits the results to that facility or encounter |
| Medication request: retrieve | The read check of the list runs first |
| Medication request: create, upsert items without `id` | Clinical write on the encounter in the body. Else 403 "You do not have permission to update encounter" |
| Medication request: create with `requester` | The requester also has clinical write on that encounter. Else 403 "Requester does not have permission to update encounter" |
| Medication request: update, delete | The read check of the list runs first. Then clinical write on the record's encounter |
| Prescription: list | The same read check as medication requests |
| Prescription: retrieve | "Can Read encounter" on its encounter, or "Pharmacist in Care" in its facility. Else 403 "Access Denied to prescription" |
| Prescription: create | Clinical write on the encounter |
| Prescription: update, set tags, remove tags | Clinical write allows any change. Otherwise "Pharmacist in Care" in the encounter's facility, else 403 "Access Denied to prescription" |
| Prescription: update by a pharmacist-only user | A new status must be `active`, `on_hold` or `completed`, else 403 "You do not have permission to update medication request prescription". Only `status` is saved. No encounter-status condition applies |
| Facility summary | "Pharmacist in Care" in the facility of the URL. Else 403 "You do not have permission to view this facility" |

"Can view clinical data about patients" counts the user's roles on the patient. These come from the departments of the patient's open encounters (and of their current locations), the patient's organizations, and a direct patient link. Closed encounters do not count.

Default role lists from the permission definitions:

| Permission | Default roles |
| --- | --- |
| "Update Encounter related clinical data" | Doctor, Nurse, Facility Admin |
| "Can Read encounter related clinical data" | Doctor, Nurse, Facility Admin |
| "Can Read encounter" | Doctor, Nurse, Facility Admin |
| "Can view clinical data about patients" | Staff, Doctor, Nurse, Facility Admin |
| "Pharmacist in Care" | Facility Admin, Pharmacist |

The permission definitions also name an Admin role. Roles are matched by name, and the only role named Admin in the database is for role organizations, which the screen that links users to departments does not offer. The lists above leave it out.

A permission refusal is HTTP 403 with the message in `detail`. A validation error is HTTP 400 with an `errors` list. A missing record is HTTP 404 with type `object_not_found`.

### Filters and ordering

Medication request list:

| Parameter | Meaning |
| --- | --- |
| `encounter` | Encounter id |
| `status` | Comma-separated statuses |
| `name` | Medicine display contains the text, case-insensitive |
| `encounter_class` | Does not work: Care answers HTTP 500. The filter is declared on `encounter__class`, but the encounter's field is `encounter_class` |
| `priority` | Exact priority, case-insensitive |
| `dispense_status`, `exclude_dispense_status` | Comma-separated dispense statuses to keep or to leave out |
| `dispense_status_isnull` | Requests with or without a dispense status |
| `facility` | Facility of the encounter. Also turns on the pharmacist read check |
| `prescription` | Prescription id |
| `product_type` | Type of the requested product: `medication`, `nutritional_product` or `consumable` |
| `medications_only` | `true` keeps requests for a medication product and requests with no product |
| `ordering` | `created_date` or `modified_date`. Without it, newest record first |

Prescription list: `encounter`, `status` (comma-separated), `facility`, a `created_date` range, and `tags` with `tags_behavior` (`any`, the default, or `all`). Ordering by `created_date` or `modified_date`.

Facility summary: a `created_date` range, `status` (one value, case-insensitive), `patient_external_id`, `encounter_external_id`, `encounter_class` (on the encounter's `encounter_class` field) and the tag filter.

Lists are paginated with `limit` and `offset` (default 14, at most 200) and return `count` and `results`.

### Upsert

`POST .../upsert/` takes `{"datapoints": [...]}`. An item with `id` updates that record; an item without one creates a record.

- An empty list fails with "No datapoints provided". More than `MAX_DATAPOINTS_PER_UPSERT` items (100 by default, set by environment variable) fails with "Too many datapoints provided".
- All items run in one transaction. If any item fails, nothing is saved and the response is HTTP 400 with one result per item.

### Notes

- Send each coded field as one `Coding` object, `{system, version, code, display}`, with a `code` from the bound value set.
- `status` has no backend default. The Care frontend starts each new medicine at `active`, intent `order`, priority `routine`, category `inpatient`, with the signed-in user as requester. It has no category or priority field.
- The Care frontend saves medicines through the upsert. Each save sends one new `create_prescription` identifier and no name, so the new medicines of one save share one prescription.
- The Care frontend never deletes a medication request. Its "remove" sets the status to `entered_in_error`.
- `requester`, `requested_product` and `prescription` are `SET_NULL` links. The prescription's `prescribed_by` is a `CASCADE` link. These rules act only when a row is removed from the database. The API delete and the model `delete()` are soft and do not trigger them.
- No deployment setting is specific to this resource.
