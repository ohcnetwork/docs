# Existing docs

Read this before you propose pages. The docs site already has a concept, a flow, or a reference for most of Care. Those pages are how you learn the words the site uses, and they are what you link to. Do not explain a neighbouring module again when a page for it exists.

The code is still the source of truth for what Care does. An existing page can be wrong. When it disagrees with the pinned code, the code wins, the page is a lead, and you say so.

## Where the pages are

The site is Docusaurus. Product pages are versioned. `versions.json` lists the versions. `docusaurus.config.js` sets `lastVersion` and `includeCurrentVersion: false`, so the site the reader sees is `versioned_docs/`, not the `docs/` folder at the repository root. On 21 Nov 2026 the latest version was 3.1 and 3.0 carried an unmaintained banner. Read the config again. Do not trust this sentence over it.

The sidebar the reader sees is `versioned_sidebars/version-<v>-sidebars.json`. The root `sidebars.js` is a leftover. Do not edit it and do not learn the site's shape from it.

These are separate, unversioned sections. A module page does not go in them:

| Folder | What it is |
| --- | --- |
| `contributing/` | How to contribute |
| `deployment/` | How to deploy Care |
| `deployments/hmis/`, `deployments/palliative/` | Playbooks for one deployment |
| `blog/` | Blog |

`versioned_docs/version-<v>/intro.mdx` is the reader's map of the four layers: concepts, flows, references, playbooks. Read it. A sentence in it can be stale. The templates in `.claude/skills/` win where they disagree.

## Find a page

Run this in the docs checkout. Use the session pin (`$S/src/docs`) when the session has one, so you match the commit you will publish to. If you were started inside the docs repository and there is no session pin yet, use that repository.

```bash
V=versioned_docs/version-3.1          # the version you are writing
find "$V" -name '*.mdx' | grep -i encounter
grep -l -i workspace -r "$V" --include='*.mdx'
```

Then open the page. For the module itself, and for each thing the module touches (patient, encounter, facility, department), read:

- its concept, if there is one
- the flow titles already listed for it
- its reference only for the terms and the links, not to copy into a concept or a flow

Record in `plan.md` which of your pages already exist and which are new. An existing page is an update. Read it before you replace it.

## Domains

List the folders rather than remembering them:

```bash
ls versioned_docs/version-3.1/concepts
ls versioned_docs/version-3.1/flows
ls versioned_docs/version-3.1/references
```

On 21 Nov 2026 the concept folders were `clinical`, `definitions`, `facility`, `medications`, `scheduling`, `billing`, `supply`, `access-governance` and `platform`. References also has `foundation`. Put the module beside the existing concept it most resembles, and link that concept. Read the folder's `_category_.json` for the label readers see. Ask the user only when two existing sections fit equally well.

`.claude/skills/care-concept-doc/references/conventions.md` explains the grouping. The folders win when that file is stale. One known case: it says the versions are kept byte-identical and authored in 3.0. They are not. `publishing.md` is the rule for versions.

## Links

A link is a relative path with `.mdx`. From a flow at `flows/<domain>/<module>/<slug>.mdx`:

| Target | Path |
| --- | --- |
| Its concept | `../../../concepts/<domain>/<concept>.mdx` |
| A sibling flow | `./other-flow.mdx` |
| A concept in another domain | `../../../concepts/<other>/<concept>.mdx` |
| A reference | `../../../references/<domain>/<concept>.mdx` |

Check the file exists before you link it. Never invent a path.

Pages that have a Malayalam translation are linked without `.mdx`. The list is whoever has a file under `i18n/ml/docusaurus-plugin-content-docs/version-<v>/`. List that folder. Do not trust a remembered list. On 21 Nov 2026, version 3.1 had translations for `intro`, `concepts/clinical/patient` and `references/clinical/patient` only.

Concepts and references show up on their own: their sidebar entry is autogenerated from the folder. A flow shows up only when its id, such as `flows/clinical/encounter/create-encounter`, is in the versioned sidebar under its module. `publishing.md` says how to add one.

## What you write, and what you link

You write concept and flow pages into the versioned docs. You do not write a reference page unless the user asks. You do not write a playbook. If a deployment playbook already walks through this module, link it.

Use the heading and the terms the existing page uses, where the pinned code still supports them. One term for one thing includes the pages already on the site.
